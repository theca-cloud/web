# Step 05: Transfers

Goal: files and folders uploaded into the current folder, files downloaded to disk, through `@theca/client` (`decisions.md`, Architecture: the same engine as the CLI, never in TypeScript): uploads in the Web Worker, downloads streamed by the Service Worker, each with its own engine; the page itself never holds one. Folder download is not V1 (`features.md`).

## Upload slots

`max_pending_uploads` is per account: two tabs uploading at once (a Web Worker each), or the web app and the CLI, share it. The engine already waits when it's full (`429 too_many_pending_uploads` at a declaration: it declares again a second later), so they take turns instead of failing; downloads take no slot. Nothing to change.

## Uploads

- **Entry points**, in a writable folder: an **Upload** button (files, several at once), an **Upload folder** button (`webkitdirectory`), and **dropping** files or folders onto the folder view (a highlighted drop zone; folders walked with `webkitGetAsEntry`, empty ones included: `folders`).
- **The worker** (`src/lib/engine.worker.ts`) gets runs: `upload` (a run ID, `{ path, file }` entries, empty folders, the library and folder) and `cancel` (a run, one file or all); it calls the WASM `upload` and posts its events back, tagged with the run. `File` objects go to the worker as they are (structured clone, no copy of the content).
- **A name already there gets a new version**, as the CLI does (`place`); nothing to ask. Conflicts (someone else's version in between) are kept as branches by the server and said in the panel.
- **The transfer panel**: a corner panel, open while a run lasts and until closed: the total progress (bytes hashed and sent, what the server already had), each file queued, done, unchanged or failed (its error by `code`: `invalid_name`, `quota_exceeded`, `network`...), a cancel per file and one for everything. Several runs at once (a drop during an upload) share it.
- **Per-file byte progress**: later (`features.md`); the panel shows the total, and each file's state.
- **The folder refreshes** when a run touching it ends (`invalidate('app:folder')`); the sidebar's libraries don't change.
- **Leaving** (closing or reloading the tab) during a run asks first (`beforeunload`); navigating within the app doesn't stop it (the worker lives with the app). An interrupted upload resumes by uploading again: what's already stored is skipped.
- No version message from the web app in V1 (the CLI has `-m`): an upload is a drop, a field there would be in the way.

## Downloads

- **Download** on a file's row menu and on its page (the current version; another version in step 06).
- **The Service Worker runs its own engine** (checked before this step: SvelteKit's separate SW build bundles the WASM module and registers the SW as an ES module in production too; a 6 MB file came back byte for byte): a request to `/sw/download/<file>?name=...` is answered by the SW with the WASM `download` stream (in order, a few chunks ahead, the reader's pace bounding the memory: `decisions.md`, Presigned URLs) and `Content-Disposition: attachment` (the name, UTF-8) and `Content-Length`. The page only follows a link to it: the browser saves the response as any download, with its own progress, pausing and cancel. No relay through the page or the worker (a Service Worker can't reach a page's Web Worker, and the download would die with that tab): it goes on whatever the tab does.
- **Without a Service Worker in control** (its very first load, before it activates; a browser without it), the link goes to the server's `/api/v1/files/{id}/content` instead, streamed by the server: the download works, the bytes just pass through it. The `/sw/` prefix never reaches the server otherwise.
- **A failure mid-way** errors the stream: the browser marks the download failed; nothing to show in the app (the browser's download list says it).

## Errors and messages

The engine's codes (`Error::kind`: `network`, `cancelled`, `invalid_name`, `folder_exists`, `corrupted`, `storage`, `source_changed`...) and the server's (`quota_exceeded`, `name_taken`...) get their messages, as the API's.

## Tests

Playwright, each test in its own library:

- Files uploaded (`setInputFiles`), downloaded (`waitForEvent('download')`) and compared byte for byte, one of several MiB (several chunks); the same name again: a new version (two in `GET /files/{id}/versions`), and unchanged content: no new one.
- A folder uploaded (its tree recreated, an empty folder included); dropped files.
- A file with a name Theca refuses fails alone, the others done; over the quota (a tiny one set through the admin API): `quota_exceeded` shown, the quota reset after.
- A cancelled upload: the file is not there; the panel says cancelled.
- The download fallback without a Service Worker (one blocked in that test's context).
- About: the engine still ready (the worker's protocol changed).

## Not in this step

Folder download (later, as zip); per-file byte progress (later); version messages; previews and other versions (step 06).

## Done when

- Every flow above passes in Playwright, in dev and in CI.
- A large file (hundreds of MiB, by hand) uploads and downloads with the tab's memory flat.
