# Step 03: Auth pages

Goal: every page a person goes through before using the app, at the paths the server links to, and the frame of the signed-in app: who is logged in, logging out, a session that expires.

## Routes

Two route groups (SvelteKit's `(group)` folders, invisible in URLs):

- **`(public)`**: reachable without a session, a centered card layout.
    - `/login`: email and password; then the TOTP code when the server answers `totp_required` (the same request again with `totp`, decisions.md: no server state between the two screens); the instance's OIDC providers (`GET /auth/oidc/providers`) as links to `/api/v1/auth/oidc/{id}/start` (a full navigation); `?error=` from a failed OIDC login (`unknown_identity`, `identity_taken`, `oidc_expired`, `oidc_refused`, `unknown_provider`) shown as a message. `email_not_verified`: a button sending the verification again.
    - `/register`: email and password; then "check your inbox" (`202`, the same answer whether the address exists or not). `registration_closed` and `email_unavailable` shown as messages.
    - `/verify?token=`: confirms at once (`POST /auth/verify`, which logs in) and goes to `/`; an `invalid_token` offers to send a new link.
    - `/reset`: asks for a link (`POST /auth/password/forgot`, `202` whatever the address); `/reset?token=`: the new password, then `/login`.
    - `/invite?token=`: accepts (`POST /invitations/accept`): an account without a password chooses one; logged in, it joins at once. Then `/`.
    - `/setup?token=`: the first-run wizard (only while `GET /setup` says `required`): the admin's email and password, the organization's name, the first storage (a server path, or S3: host, region, bucket, the access and secret keys as **file paths**, path-style); the token goes as `X-Theca-Setup-Token`. Done: logged in, to `/`.
- **`(app)`**: everything else. Its layout loads `/me` once (shared with the pages below through `load`): a `401` leads to `/login?next=<the page>`, `503 setup_required` to `/setup`. A minimal frame: the account's email, a menu with logout; step 04 fills it.

## Behaviour

- **After login, back to `next`**: only a path of the app (starting with `/`, not `//`): never an outside URL (an open redirect). Vitest covers the check.
- **Every API error shown by its `code`**, through messages (`CLAUDE.md`); an unknown code falls back to a generic message with the server's.
- **Forms**: native HTML validation where it fits (`type="email"`, `required`), the server's answer otherwise (`weak_password`: its message says the rule). Submitting disables the button; errors stay next to the form, the input kept.
- **The API version** (`/api/version`): checked once when the app starts; a server without `v1` shows a blocking message.
- **Logout**: `POST /auth/logout`, then `/login`.
- `shadcn-svelte` components as needed: button, input, label, card, alert, dropdown menu.

## `core`: what the login page can't know

Whether registration is open (the "create an account" link) and the instance's name (`instance_name`, "shown in emails and the web app", decisions.md): a public `GET /api/v1/instance` (`name`, `registration`), released first (`core` `0.10.0`), pinned here.

## Tests

The email flows need emails, and the setup page a fresh server: both added to the dev compose and to CI.

- **Mailpit** (as `core`'s dev compose has) in `docker-compose.yml`, its API on `127.0.0.1:8095` (8025 is often taken by another project's Mailpit; SMTP stays inside the compose network), and as a CI service; `scripts/setup.sh` sets the server's SMTP settings to it. The tests read the links from Mailpit's API.
- **A second, fresh server** for the setup wizard (never set up: its own database, `SETUP_OPEN` off so the token matters, read from its logs or set up through its URL): a compose service and a CI service, on the same Postgres with another database; on `127.0.0.1:8094` in dev.
- **Playwright flows**: a wrong password then the right one, back to `next`; logout; an expired session (its cookie removed) leads to `/login?next=`; registration (setting `registration = open` through the admin API) to the email's link, logged in; a password reset through its email; an invitation (the admin adds an unknown address) through its email; the setup wizard on the fresh server; `/login?error=unknown_identity` shows its message.
- **Not here**: logging in with a TOTP code (needs TOTP turned on: step 07, with its page); an OIDC login itself (needs a provider: later, if an Authelia or Dex container proves worth it). Only the `?error=` messages are tested.

## Not in this step
