# Global roadmap

From an empty repo to the V1 web app. Each step gets its own detailed file (`01. ...`, `02. ...`), written right before implementing it. Scope and design: see `../docs` (`features.md`, `decisions.md`, Architecture).

The order builds the frame first (the app, its workers, the `core` changes it needs), then the pages, the file pages before the account, organization and admin ones: what the app is for comes first.

## Steps

| # | Step | Done when |
|---|---|---|
| 1 | **Skeleton** | The app builds and is served by the server; one Playwright test passes in CI |
| 2 | **`core`: shared client code and gaps** | The engines, folder upload and the missing endpoints are in a `core` release, pinned here |
| 3 | **Auth pages** | Login (TOTP, OIDC), setup, registration, verification, reset and invitations work end to end |
| 4 | **Browse** | Organizations, libraries and folders are browsed by URL; mkdir, rename, move, copy and delete work |
| 5 | **Transfers** | Files and folders upload, files download to disk, with progress and cancel, through the workers |
| 6 | **Versions, trash, search, previews** | Each works end to end |
| 7 | **Account** | Password, TOTP, identities, sessions, app passwords, export and deletion work |
| 8 | **Organization** | Members, invitations, ownership, library members, namespaces, its OIDC provider and its trash work |
| 9 | **Admin** | Accounts, organizations, storages, identity providers, settings and jobs work |
| 10 | **First release** | The `web` image `0.1.0` is published |

## Contents

1. **Skeleton**: SvelteKit + TypeScript (`adapter-static`, SPA fallback), Svelte 5, Tailwind (its Vite plugin); the npm scripts `scripts/ci.sh` calls (`lint`, `check`, `build`, `test`, `test:e2e`); `src/lib/api.d.ts` from `scripts/api-types.sh` and `openapi-fetch` on those types (API errors typed by their `code`); the Vite proxy (`/api`, `/dav` to :8093); **the Web Worker** (owns the `@theca/client` engine) and **the Service Worker** (registered from the start, the download path of step 5), both empty frames; the CI green with one Playwright test.
    - CI serves the app at `http://theca:8080`, not a secure context: no Service Worker there. Playwright's Chromium treats that origin as secure (`--unsafely-treat-insecure-origin-as-secure`).
2. **`core`: shared client code and gaps** (a `core` step, in `../core/roadmap/`, released, then the pin bumped here):
    - **Shared client code in `theca-client`**: what every client needs, written once. The CLI's folder upload (the tree recreated like `mkdir -p`, existing folders reused, failures reported while the others go on, unchanged files not versioned) moves from `cli/src/transfer.rs` into `theca-client`; the CLI keeps terminal I/O and its virtual filesystem, and bumps its pin to use the moved code.
    - **The WASM API** (`wasm.rs`) exposes the staged `Uploader` and `Downloader`: several files at once, cancel one file or everything, new versions of existing files, messages, folder upload, progress per file; downloads into a sink fed to JavaScript (the Service Worker's stream).
    - **Endpoints**: library members (list, add, change role, remove), dedup namespaces (create, list, add and remove libraries), company organizations (created by a user, renamed by their owner).
    - **`NodeInfo.ancestors`** (`[{id, name}]`, root to parent): the breadcrumb's links in the request the page makes anyway. The same climb as `path` (one query, `path` being their names joined): no extra cost, no flag.
3. **Auth pages**, at the paths the server links to: `/login` (password, TOTP when asked, the instance's OIDC providers, `?error=`), `/setup?token=`, `/register`, `/verify?token=`, `/reset?token=` (and asking for one), `/invite?token=`; logout; an expired session leads to `/login`, back to the page afterwards; the API version checked (`/api/version`).
4. **Browse**: URLs by ID, `/<org>/<lib>/<node>` (`/<org>` its libraries, `/<org>/<lib>` the root, a file's node its preview); `/` lists the account's organizations and libraries (the personal one as "My files"); breadcrumbs from `ancestors`; folder listing with sizes and dates; create a library or folder, rename, move, copy (onto an existing file: asked, then `replace`), delete to the trash.
5. **Transfers**: upload files and folders (picked, or dropped) into the current folder, a new version when the name exists, an optional message; downloads of files streamed to disk through the Service Worker; a transfer panel (progress per file, cancel one or all); errors per file (a name refused, quota exceeded) without stopping the others.
6. **Versions, trash, search, previews**: a file's version tree (numbers, messages, authors, dates), restore and download of any version; the library's and the organization's trash, restore and purge (libraries included); name search across libraries; previews the browser renders (PDF, image, video, sound, text) from `/files/{id}/content`.
7. **Account**: email and password, TOTP (setup with its QR code, recovery codes, disable), OIDC identities (link, remove), sessions (list, revoke), app passwords (create with a scope and read-only, list, revoke), export, account deletion.
8. **Organization** (the owner's pages): members and invitations, ownership transfer, library members and roles, namespaces (with the warning when merging: decisions.md, Trust boundary), its OIDC provider, its trash, deletion; creating and renaming a company organization.
9. **Admin** (instance admin): accounts, organizations (quotas, suspension), storages and the default, instance identity providers, settings, jobs (runs, trigger).
10. **First release**: `scripts/release.sh`, the `web` image `0.1.0` on the registry; `ce` assembles it with `core`.

## Testing

- **End to end with Playwright against the real server**: each step's flows (login, upload, download, versions, trash, ...), in CI on the server serving the build (`WEB_DIR`), as in production. Each test in its own library, so tests don't depend on each other.
- **Vitest** for logic with edge cases and no server (the `fetch` wrapper's errors, formatting, URL parsing).
- The transfer engine itself is `theca-client`'s, tested in `core`: here, only that the app drives it.

## Out of scope for V1

Folder download (as zip, later: `features.md`); sharing and public links (V2); previews through presigned URLs (V2: the Service Worker exists from step 01, for downloads; V2 adds its Range requests); installable app (PWA); dark mode, internationalization (English only); thumbnails, editors, favorites. See `../docs/features.md`.
