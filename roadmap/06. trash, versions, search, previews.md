# Step 06: Trash, versions, search, previews

Goal: what's deleted can be found and brought back, a file's history used, any file found by name, and the files a browser can show shown, without loading big files for nothing (`features.md`: previews through the server's streaming endpoint in V1; through the Service Worker in V2).

## `core` first: search in a context

`GET /search` takes a `library` today. Added: `organization` (its libraries the account reaches) and `folder` (that folder and below: each candidate checked by climbing to the folder, before the limit of 50, so the limit counts only hits inside it). One of them at most; none: everywhere. A `core` minor release, pinned here.

## Where: the sidebar and the context

- **Search at the top of the sidebar** (the entry reached for first), **Trash at its foot**, above the account (rarely visited). Built switchable at first, both placements compared in the browser together, the other one dropped.
- **Search and trash follow the context**: opened from a folder, they cover that folder and below; a selector widens them, folder → library → organization → everywhere. The context is where the user is (the URL); `/search?q=&in=<folder|library|organization>` and `/trash?in=...` keep it in the address.

## Trash

- **Its scope**, as the context says: an organization's trashed libraries (`GET /organizations/{id}/trash`) and each library's trash (`GET /libraries/{id}/trash`, in parallel: libraries are few); a library's trash; a folder's: the library's trash filtered by path (`TrashEntry.path`). Everywhere: every organization.
- Each item: its name, where it was, when it was deleted, its size.
- **Restore**: back where it was (or the library's root if its folder is trashed too; renamed ` (restored)` if the name was taken since: the server's rule), several at once (`POST /nodes/restore`); a trashed library with its own restore.
- **Delete for good**: confirmed first (it can't be undone), several at once (`POST /nodes/trash`, `permanent`); a library too. **Empty the trash** of the scope: the same, for all of it, confirmed.
- The retention (purged after N days, the admin's setting) isn't shown: the setting is admin-only.

## Versions

On a file's page, its history (`GET /files/{id}/versions`), as a list, newest first: each version's number (the server's, RCS-style: `2.1.1` says it's a branch, decisions.md, File history), date, author, size and message, the current one marked. No tree drawn: the numbers say the branches, a drawing would confuse more than help.

- **Restore** a version: it becomes current (`POST /files/{id}/versions/{version}/restore`); the next upload branches from it.
- **Download** and **preview** any version (`?version=`).

## The file's page

Its name, size, date; its actions (download, rename, move, copy, delete: those of its row in the folder, step 04); its preview; its versions.

## Search

The field in the sidebar → `/search?q=&in=`: files and folders whose name contains it, in the context (above), at most 50, at least 3 characters (said under the field). Each result: name, library, path, size; a file opens its page, a folder the folder.

## Previews

From the server's stream (`/api/v1/files/{id}/content`, `?version=`, `Range`); the kind from its `Content-Type` through a `HEAD` request (the server's rules by extension, not repeated here). Nothing ever runs script:

- **Video and audio**: the browser's player, `preload="metadata"`: only the start is loaded until play, then streamed (seeking by `Range`).
- **Text and code**: its first 1 MiB (`Range`), in a `<pre>`; always shown (cheap).
- **Images**: an `<img>`.
- **SVG**: the bytes fetched (the server serves them as text) and shown as an `<img>` from a `blob:` URL: browsers never run an SVG's scripts in an `<img>`.
- **HTML**: raw (its source, as text) or rendered, a switch. Rendered: an `<iframe sandbox>` without `allow-scripts` (no JavaScript runs), with a content policy blocking outside resources (a tracking image would tell someone the file was opened).
- **PDF**: the bytes fetched and shown from a `blob:` URL in a frame: the server's `Content-Security-Policy: sandbox` doesn't apply to it, so the browser's viewer works.
- **Shown at once below 5 MiB**; above, a "Show preview" button: a preview shouldn't load a big file nobody asked to see. Video, audio and text load little whatever the size, and are always shown.
- Anything else: no preview, the download button.

## Tests

Playwright, each test in its own library:

- Trash: a file and a folder deleted, listed in the folder's trash, one restored (back in its folder), the other deleted for good after confirming; the scope widened to the library, then the organization (a trashed library there, restored).
- Versions: a file uploaded twice, both versions listed (the current one marked), the first restored and downloaded (its bytes).
- Search: from a folder, a file inside found and one outside not; widened to the library, both; two characters: the hint; a result opened.
- Previews: an image loaded (`naturalWidth`); a text file's content; an SVG as an image; an HTML file raw, then rendered without running its script (a script setting a marker: absent); a PDF in its frame; a file above 5 MiB: the button, then the preview; an unknown type: the download button only.

## Not in this step

Previews through the Service Worker (V2); thumbnails and a grid view (V2, `features.md`); the trash's retention shown; search by content (never: names only, decisions.md, Search).
