# Step 02: `core`: shared client code and gaps

Goal: everything the web app needs from `core`, in one `core` release, pinned here. The work happens in `../core` (its own branch, commit, release: `0.9.0`), then in `cli` (the pin bumped, the moved code used). Planned here because the web app is why it exists; `core`'s roadmap gets a line pointing here.

`theca-client` is `core`'s `crates/client`: the CLI compiles it natively from the Gitea Cargo registry; `core`'s release builds it to WASM (`wasm-pack`) as the npm package `@theca/client` pinned here. Browser-only code is behind `cfg(target_arch = "wasm32")`, absent from native builds.

Rule for what moves: **code every client needs lives in `theca-client`**, written once; a client keeps only its platform (terminal, files on disk, the browser) and its UI.

## 1. Shared client code in `theca-client`

From the CLI's `src/transfer.rs` and `src/paths.rs`, without their terminal output:

- **Placing uploads**: a file as `name` in a remote folder becomes a new file, or a new version of the file already there with that name (case-insensitive, as the server compares), based on its current version; a folder with that name is an error for that file. Today `prepare` in the CLI.
- **Folder uploads**: a tree of relative paths (folders parents first, files with their folder) placed under a remote folder: the folders created in batches (`POST /nodes/{id}/folders`, `mkdir -p`), what already exists read from one tree listing (`GET /nodes/{id}/tree`), each file placed as above. A file or folder failing (an invalid name) is reported and the others go on. Today `tree_uploads` in the CLI.
- The name key the server compares by (`path_key`).

Walking a local folder stays each client's (`std::fs` in the CLI, the browser's dropped or picked files in the web app); they hand `theca-client` relative paths and `Source`s.

## 2. The WASM API (`wasm.rs`)

Today: one file, a new one only, one global cancel. After: the engines the CLI uses, through a small API the Web Worker calls.

- **Uploads**: `upload(id, entries, folders, library, folder, message, onEvent)`, entries `{ path, file }` (`path` relative, `a/b/c.txt` for a folder upload, `c.txt` for a single file): one call for files and folders, placed as in section 1, through one `Uploader` (several files at once, a chunk two files share uploaded once). `cancel(id, path)` cancels one file of the run `id`, `cancel(id)` all of it (several runs at once: the user drops more files).
- **Events** to `onEvent`: the overall progress (bytes hashed, uploaded, skipped, out of the total), and each file's outcome (`done`: its file, version, conflict, unchanged; `failed`: its error). Per-file byte progress: later (`features.md`); the panel shows the total, and each file queued, done or failed.
- **Downloads**: `download(file, version)` returns a `ReadableStream` of the content **in order**, which the Service Worker serves as the download's response (step 05). Built: `theca-client`'s `stream`, the manifest then the chunks through `futures`' ordered `buffered(n)` (4 in a browser): in order, at most `n` chunks held, nothing fetched until the stream is read, so a slow disk pauses the download. The bounded window planned in the `Downloader` wasn't needed: the engine is unchanged, and the `download` module builds for WASM (`FileSink` and `FileSource` stay native). The name and size come from the listing the app already has.
- **Errors** reach JavaScript as `{ code, message }`: the API's `code` when the server answered (`name_taken`, `quota_exceeded`...), the engine's otherwise (`cancelled`, `network`, `invalid_name`, `corrupted`...): the web app shows messages by `code`, as for its own API calls.
- `ThecaClient` keeps one `Client` (the session cookie, `credentials: include`) for both engines.

## 3. Endpoints

- **Library members** (V1 roles `read`, `write`; managed by the organization's owner, its only administrator: decisions.md, Authorization): `GET /libraries/{id}/members` (its members and the owner), `PUT /libraries/{id}/members/{user}` (adds, or changes the role: one idempotent call instead of `POST` and `PATCH`), `DELETE`. Invited users (not joined yet) can be added (decisions.md).
- **The organization's libraries, to its owner** (`GET /organizations/{id}/libraries`, with their member counts): the owner manages libraries it isn't a member of, which `/libraries` doesn't list.
- **Dedup namespaces** (the organization's owner): `GET /organizations/{id}/namespaces` (with their libraries), `POST` (a name), `PATCH` (rename), `DELETE`; a library added to or removed from a namespace (`PUT` / `DELETE /namespaces/{id}/libraries/{library}`), taking effect at once both ways (decisions.md, Trust boundary). The UI's warning when merging is the web app's. **Namespaces at library creation become the owner's only** (`403 owner_required`): any member could otherwise create a library in another's namespace and probe its content (found while writing this step).
- **Company organizations**: `POST /organizations` (a name; the caller becomes its owner), `PATCH /organizations/{id}` (rename, the owner), `GET /organizations/{id}` (any member: name, whether the account owns it, quota and usage). Who may create one is an instance setting, `organization_creation`: `anyone` (the default) or `admins`, so an instance or the SaaS (billed per organization) can restrict it.

## 4. Fields the app needs

Each one an added field (not breaking):

- **`NodeInfo.ancestors`** (`[{id, name}]`, root to parent): the breadcrumb's links. The same climb as `path` (one query, `path` being their names joined): no extra cost, no flag.
- **`Me.instance_admin`**: whether to show the admin pages.
- **`Membership.owner`**: whether the account owns that organization (its settings, members, namespaces); today only `GET /organizations/{id}/members` says it, one request per organization.
- **Quota and usage** for every member, in `GET /organizations/{id}` rather than `Membership`: the usage is a sum over the organization's chunks, which `/me` (every page load) shouldn't compute.
- **`Library.writable`**: whether the account may write in it (its role and its credential's read-only cap, from `library_access`): the app hides what it can't do instead of failing on it.

## Tests

- `core`: each endpoint in-process, as every `core` step (access refused to non-owners, invited members, namespaces across organizations refused by the database); the moved placing logic natively (new file, new version, name taken by a folder, case-insensitive match, a tree into an existing folder); the download stream (in order, against the real server: the smoke test).
- `cli`: its batch tests unchanged and green after the bump (the moved code behaves as before).
- The WASM API itself: through the web app's Playwright flows (step 05).

## Breaking

- The WASM API's `upload` changes (the web app is its only user, before its first release): an entry in `../docs/BREAKING.md`.
- The Rust API of `theca-client` only grows (the CLI moves to the new functions).
