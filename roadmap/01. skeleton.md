# Step 01: Skeleton

Goal: an empty but complete app with every tool and check in place, and the plumbing every later step stands on proven end to end: the API through the `fetch` wrapper, the engine in its Web Worker, the Service Worker. Later steps only add pages.

No page yet: one placeholder page showing what the plumbing reports.

## The `fetch` wrapper (`src/lib/api.ts`)

Typed from `api.d.ts` (`paths`): a call names its method and path, its parameters, body and answer are checked by TypeScript.

- **`openapi-fetch`**, not our own: it is that thin wrapper (a few KB, no code generation, made for `openapi-typescript`'s output), and typing path parameters and bodies by path is the part we would otherwise write and maintain. Errors: one function turns a non-2xx answer into an `ApiError` (`status`, `code`, `message`, `chunks`), the API's error schema.
- Same origin, the session cookie sent by the browser (`httpOnly`: JavaScript never sees it). Bodies are JSON (the CSRF rule: decisions.md, Authentication).
- Vitest: the error mapping.

## The engine's Web Worker (`src/lib/engine/`)

The worker owns `@theca/client` (built `--target web`: an `init()` loading the `.wasm`); the page talks to it with `postMessage`, a small typed protocol (request ID, kind, payload; answers and progress events back). No library (Comlink): the protocol is a few message kinds.

- In this step the worker loads the WASM module and answers one message (`ready`), so a failure to load it in dev or in the built app shows now, not in step 05.
- One worker for the app, started on first use.
- Vite: `@theca/client` excluded from dependency pre-bundling if its `.wasm` URL breaks there (`optimizeDeps.exclude`).

## The Service Worker (`src/service-worker.ts`)

SvelteKit registers it by itself. In this step it only takes control (`clients.claim()`) and lets every request through: no caching (the app isn't installable in V1). Step 05 adds the download path (a streamed response fed by the engine).

## Tests and CI

- **Playwright**, Chromium only (Firefox and WebKit later, if a bug shows they're worth the CI time). `baseURL` is `THECA_TEST_APP` when set (CI: the server serving `build/`); unset, the config starts `npm run dev` (its `webServer`), against `scripts/dev.sh`'s server.
- **CI only: the insecure origin.** CI serves the app at `http://theca:8080`, not a secure context, so no Service Worker. Chromium is launched there with `--unsafely-treat-insecure-origin-as-secure=http://theca:8080`. **To check**: the session cookie is `Secure`; the flag should also let Chromium keep it on that origin. If it doesn't, decide here (before step 03 needs logins).
- **The first test** (`tests/e2e/skeleton.test.ts`): the placeholder page loads; the engine worker answers `ready`; the Service Worker controls the page; logging in as the dev admin through the wrapper (`POST /auth/login`, then `GET /me`) works, which proves the proxy (dev) and the cookie (CI).
- `.woodpecker/ci.yaml`: the Playwright image's tag set to the installed `@playwright/test` version.
