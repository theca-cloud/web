# Step 01: Skeleton

Goal: an empty but complete app with every tool and check in place, and the plumbing every later step stands on proven end to end: the API through the `fetch` wrapper, the engine in its Web Worker, the Service Worker. Later steps only add pages.

- **Created with `npx sv create`**, template `minimal`, types `ts`, add-ons: `prettier`, `eslint`, `vitest` (`unit` only: components are covered by Playwright against the real server), `playwright` (no demo), `tailwindcss` (`forms`), `sveltekit-adapter` (`static`), `paraglide` (`en`, no demo), `ai-tools` (Claude Code, Svelte's remote MCP: `.mcp.json` committed). Then trimmed: whatever it generates that we don't use goes (paraglide's server hooks and locale links: one locale, no SSR; examples, `.vscode/`, `AGENTS.md`, whose Svelte MCP note moved to `CLAUDE.md`).
- **SvelteKit 3**: no `svelte.config.js` (its options are the Vite plugin's), and `$lib` is gone: `#lib/...`, a Node subpath import (`package.json`'s `imports`), written with the file's extension (`#lib/engine.js`).
- **Svelte 5** (runes), **Tailwind v4** through its Vite plugin (no config file; `prettier-plugin-tailwindcss` sorts classes).
- **`shadcn-svelte`** initialized with the **Nova** preset (Geist, reduced spacing: dense listings), neutral colors (`components.json`, its theme tokens in `layout.css`, `src/lib/components/ui/`); components added as pages need them (on `bits-ui`; icons `@lucide/svelte`), none yet. Its `init` only asks interactively for a named preset: `--preset` takes the code `encodePreset` gives (Nova: `b2fA`).
- **`paraglide`**: `messages/en.json`, the base and only locale; every string the app shows is a message (`m.key()`), the placeholder's included. Playwright finds elements by role and accessible name, from the same messages.
- **Node 24** in `.nvmrc` (the README and CI's version).
- **`adapter-static` with `fallback: 'index.html'`**: the server answers `index.html` for every unknown path (`core/crates/core/src/web.rs`), so deep links and reloads work; routing is client-side, real paths (decisions.md, Architecture).
- **`openapi-typescript` isn't a dependency**: it wants TypeScript 5 as a peer, the app has 6; `scripts/api-types.sh` runs a pinned version through `npx`. The generated file is `openapi.d.ts`, not `api.d.ts`: `./api` would resolve to the wrapper itself.
- **`@theca/client` pinned exactly** (`0.8.0`, the current `core` release): the one pin, read by `scripts/api-types.sh`. Bumped in step 02.
- **npm scripts** (`scripts/ci.sh` calls them): `lint` (`prettier --check` and `eslint`), `check` (`svelte-check`), `build`, `test` (`vitest run`), `test:e2e` (`playwright test`).

## The `fetch` wrapper (`src/lib/api.ts`)

Typed from `openapi.d.ts` (`paths`): a call names its method and path, its parameters, body and answer are checked by TypeScript.

- **`openapi-fetch`**, not our own: it is that thin wrapper (a few KB, no code generation, made for `openapi-typescript`'s output), and typing path parameters and bodies by path is the part we would otherwise write and maintain. Errors: `call` turns every answer into a `Result` (`src/lib/result.ts`): the data, or an `ApiError` (`status`, then the API's error schema: `code`, `message`, `chunks`), `unknown` for a body that isn't the API's, `network` when no answer came. It never throws (`CLAUDE.md`, errors are values).
- Same origin, the session cookie sent by the browser (`httpOnly`: JavaScript never sees it). Bodies are JSON (the CSRF rule: decisions.md, Authentication).
- Vitest: the error mapping, and `result.ts`'s `combineAll` and `expect`.
- `src/hooks.client.ts`: `handleError` logs what reaches the error page and shows a generic message.

## The engine's Web Worker (`src/lib/engine.ts`, `engine.worker.ts`)

The worker owns `@theca/client` (built `--target web`: an `init()` loading the `.wasm`); the page talks to it with `postMessage`, a small typed protocol (request ID, kind, payload; answers and progress events back). No library (Comlink): the protocol is a few message kinds.

- In this step the worker loads the WASM module and answers one message (`ready`), so a failure to load it in dev or in the built app shows now, not in step 05.
- One worker for the app, started on first use.
- Vite: workers built as ES modules (`worker.format: 'es'`: `@theca/client` is one), and `@theca/client` excluded from dependency pre-bundling, which breaks its `.wasm` URL (`optimizeDeps.exclude`).

## The Service Worker (`src/service-worker.ts`)

SvelteKit registers it by itself. In this step it only takes control (`clients.claim()`) and lets every request through: no caching (the app isn't installable in V1). Step 05 adds the download path (a streamed response fed by the engine).

## Tests and CI

- **Playwright**, Chromium only (Firefox and WebKit later, if a bug shows they're worth the CI time). `baseURL` is `THECA_TEST_APP` when set (CI: the server serving `build/`); unset, the config starts `npm run dev` (its `webServer`), against `scripts/dev.sh`'s server.
- **CI only: the insecure origin.** CI serves the app at `http://theca:8080`, not a secure context, so no Service Worker. Chromium is launched there with `--unsafely-treat-insecure-origin-as-secure=http://theca:8080`, which also keeps the `Secure` session cookie. **Full Chromium** (`channel: 'chromium'`): Playwright's default headless shell ignores the flag (checked: no secure context, no cookie). Checked locally as CI runs it: the built app served by a second server container, Playwright's image on the same Docker network.
- **The first test** (`tests/e2e/skeleton.test.ts`): the placeholder page loads; the engine worker answers `ready`; the Service Worker controls the page; logging in as the dev admin through the wrapper (`POST /auth/login`, then `GET /me`) works, which proves the proxy (dev) and the cookie (CI).
- `@playwright/test` pinned exactly (`1.63.0`), the Playwright image's tag in `.woodpecker/ci.yaml` set to it.
- `scripts/release-ci.sh` reads the version with `jq` (Prettier indents `package.json` with tabs, which its `sed` didn't expect).
- Prettier skips Markdown (the docs' style), YAML (as in `core` and `cli`), the generated types and inlang's files.
