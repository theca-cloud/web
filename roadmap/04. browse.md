# Step 04: Browse

Goal: the app's frame (`decisions.md`, Look: a sidebar, no top bar, teal) and moving around and organizing files: organizations, libraries and folders by URL, and every operation that doesn't transfer content (create, rename, move, copy, delete). Uploads and downloads are step 05.

First a `core` release, so the UI is built on the final API (below).

## URLs

IDs, readable enough through the page itself (breadcrumbs, titles):

- `/`: to the personal organization (`/<its id>`), the one every account has; an account with none (only invited into a company) to its first organization.
- `/<org>`: the organization's libraries the account is in, a table (name, writable or read-only); creating one; for its owner, a link to its settings (step 08).
- `/<org>/<lib>`: the library's root folder.
- `/<org>/<lib>/<node>`: a folder; a file shows its page (name, size, modified; its actions; preview and versions in step 06, download in step 05). No `/file` suffix: the page fetches the node anyway (its ancestors), which says its kind, and a node never changes kind; a suffix would only add URLs that contradict the server.
- Each segment is checked against UUIDs (a param matcher, `src/params/uuid.ts`): anything else is the app's 404, never a request with a malformed ID. An ID the account can't reach: the server's 404, shown inside the frame.

## The frame

`shadcn-svelte`'s `sidebar` component (collapsible, a sheet on narrow screens), in the `(app)` layout, in sections: a top one for entries to come ("Shared with me", recent files, the trash, search: empty for now), then the organizations.

- **Organizations**, the personal one first as "My files", each with its libraries (`/me`'s memberships, `/libraries` grouped by organization), the current one highlighted; a "+" to create a library where the account may.
- **At its foot**: the account menu (email; logout; the account's pages in step 07, the admin's in step 09).
- **The page**: breadcrumbs (organization › library › `NodeInfo.ancestors` › the node), each a link, then the content.
- Teal as the accent: `--primary` (and `--ring`, `--sidebar-primary`) in `layout.css`, light only (dark mode later, `features.md`).

## The folder table

Folders first, then files, by name (the server's order); a click on a column sorts by it (name, size, modified), in the browser. A folder opens on click; a file its page.

- **Actions**, on each row (a menu) and on the selection (checkboxes, a bar above the table when some are checked): rename (one), move, copy, delete.
- **Create a folder**: a dialog with its name.
- **Rename**: a dialog; `name_taken` and `name_invalid` shown in it.
- **Move and copy**: a dialog picking the destination folder, browsing the organization's libraries and their folders (a move or copy never leaves the organization: `other_organization`). Onto an existing file: asked, then sent again with `replace` (decisions.md, Moves and copies: a move grafts the histories, a copy adds a version). Folders are never replaced (`name_taken` shown).
- **Delete**: to the trash at once, no confirmation, a toast with **Undo** (a restore). Not a delayed "Cancel": the delete is real at once (closing the tab doesn't lose it, other devices see it). The trash itself is step 06.
- **Libraries**: renamed and moved to the trash from their own menu (in the sidebar, and on the organization's page), with the same undo.
- **Read-only**: a library with `writable` false shows no write action (no create, rename, move, delete; copy only out of it).
- Several items at once: one request (the API takes lists), each item its own outcome: failures listed in one toast, the others done.
- Errors by `code`, where the action happened (the dialog, or a toast for row actions).
- Empty states: a library without files, an organization without libraries.

## `core` first: node operations take lists (`0.11.0`)

`decisions.md` (API contract) says every endpoint acting on several things takes a list, one item being a list of one; node operations still take one (`PATCH /nodes/{id}`, `DELETE`, `copy`, `restore`). Fixed before 1.0, shaped like `POST /files/commit` (each item in its own transaction, its own outcome: partial success):

- `PATCH /nodes`: `[{ id, name?, parent?, replace? }]` (rename, move).
- `POST /nodes/copy`: `[{ id, parent, name?, replace? }]`.
- `POST /nodes/trash`: `{ nodes: [ids], permanent }` (a `POST`: some proxies drop a `DELETE`'s body).
- `POST /nodes/restore`: `[ids]`.
- The single-node routes go (breaking, `BREAKING.md`); `GET /nodes/{id}` stays. Libraries keep theirs (one at a time, and not nodes).
- `theca-client`'s methods take lists; the CLI follows (`rm a b c` in one request), released after.
- With the logout fix already on `core`'s `dev`.

## Tests

Playwright, each test in its own library (created through the API, deleted at the end):

- The frame: the sidebar lists the dev admin's organization and libraries; `/` lands on the personal organization; a deep link reloaded opens the same folder; breadcrumbs lead back up.
- A folder created, renamed, moved into another, copied (onto an existing file: replaced after confirming), deleted then undone; several items moved at once.
- A library created from the sidebar, renamed, trashed then undone.
- Errors: a name taken (shown in the dialog), a move into itself.
- Read-only: a second account added with `read` (through the admin's API) sees no write action.
- A malformed ID in the URL: the 404 page.
