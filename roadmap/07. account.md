# Step 07: Account

Goal: everything an account does to itself, from the web (`features.md`: identities, app passwords, sessions, TOTP, deletion and export, all V1): its password (the email never changes), TOTP, its ways to log in, its sessions and app passwords, its data exported, the account deleted.

## `core` first: the gaps

The API covers most of it (`/auth/totp*`, `/auth/identities`, `/auth/oidc/{provider}/link`, `/auth/sessions`, `/auth/app-passwords`, `/me/export`, `DELETE /me`). Missing:

- **Password strength, zxcvbn**: the instance setting `password_strength` (0 to 4, default 3, `PATCH /admin/settings`), enforced by the server wherever a password is chosen (registration, setup, reset, invitation, change): `weak_password` below it, with zxcvbn's feedback. **The account's email is always a user input** (a password made of it scores low), on every page: typed (registration, setup), the account's (change), or the link's (reset, invitation: below). 0 skips the check. The 8-character floor stays at every level. `GET /instance` says the level, for the pages to show it.
- **One scorer for both sides**: the check lives in `common` (the `zxcvbn` crate, pure Rust, builds for WASM), so the server and `@theca/client` score with the same code and dictionaries: the bar never says "strong" for a password the server refuses. The page asks the Web Worker (the engine's WASM is already there; the page holds no engine), debounced.
- **The email behind a link**: the reset and invitation pages hold only the token. Added: `POST /auth/token` `{token}` → `{email}` (not consumed; a `POST`, the token out of logs; `invalid_token` if expired or used). Holding the token proves the inbox, so the address tells nothing new. The invitation page shows it too ("joining as ...").
- **Changing the password while logged in**: only the forgotten-password email exists, and its reset logs out every session, this one too. Added: `POST /auth/password` `{current, new}` (a full session), logging out every *other* session. An account without a password (OIDC only) adds one through the reset email, as today (the reset upserts the password identity).
- **Linking an identity lands on `/`**: it should land back on `/account` (the callback knows it's a link).

**The email never changes**: it's the account's identity (login, invitations, the reset and its proof of inbox), and a change flow is one more way to take an account over. A mistyped address at registration never gets verified, so never logs in: register again. No `Me.verified` either: an unverified account can't log in, so a session's account is always verified.

A `core` minor release, pinned here.

## Where

`/account`, from the account menu at the sidebar's foot ("Account", above "Log out"). **One page, in sections**, no sub-pages: each section is short, and one page is found with the browser's search. In order:

1. **Email**: the address, read only.
2. **Password**: **Change** (current, new, with the strength bar). Without one: **Set a password**, sending the reset email.
3. **Two-factor**: off: **Turn on**: a dialog with the QR code (`uqr`, tiny, SVG, no dependencies) and the secret as text (for a password manager), a first code to confirm, then the recovery codes, shown once (copy, download as `.txt`). On: **New recovery codes** and **Turn off**, each with a code. Only for accounts with a password (TOTP guards password logins).
4. **Ways to log in**: the password and each OIDC identity (its provider's name); **Remove** (never the last: the server's `last_identity`); **Link** one per provider not yet linked (`GET /auth/oidc/providers`, then the `link` POST and its URL).
5. **Sessions**: each one's name, browser (the user agent, shortened), IP, last seen, this one marked; **Revoke** for the others, never this one (the account menu's **Log out** does).
6. **App passwords**: each one's name, scope (everything, an organization, a library), read-only, last used; **Revoke**, confirmed. **Create**: name, scope, read-only; the password shown once with a copy button, and what it's for (WebDAV's address, the CLI's login).
7. **Export**: downloads the JSON (`theca-export.json`); a line says files come through WebDAV or the CLI.
8. **Delete the account**: a dialog (the password if it has one, a TOTP code if on); `owns_organizations` and `last_admin` explained. Then to `/login`.

**A restricted session** (logged in through an organization's provider: `full_session_required` for most of this) sees only what it may: sections 5 and 6; a line says why the rest is hidden. The current session's `restricted_to` says it.

## The strength bar

Under every new-password field (registration, setup, reset, invitation, change): four segments filled to zxcvbn's score, coloured from red to the accent, its feedback as text below, the instance's level marked; the submit button stays enabled (the server answers, the bar only guides). Level 0: the bar shown, as an indication only.

## Tests

Vitest: the user agent shortened. Playwright, against the real server: a weak password refused at registration (the bar and the server agree); the password changed (the old one refused at login, the session kept); TOTP turned on (a code computed in the test from the secret, `otpauth`'s algorithm in a few lines), required at the next login, turned off; a session revoked (its page sent to the login); an app password created, used over WebDAV (`fetch` with Basic auth), revoked, refused; the export downloaded; an account registered, then deleted (its login refused). OIDC linking: no provider in the test server, left to the manual check.
